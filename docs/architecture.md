# 总体架构文档 · 智汇于庄

> 本文档描述《智汇于庄：基于大模型与高并发引擎的特色产业数字助农中台》的总体技术架构，
> 是后续各模块（backend / ai-service / web / h5 / mobile）设计与实现的总纲。

## 1. 设计目标与原则

| 目标 | 说明 |
|------|------|
| 三端分离、各司其职 | C 端极致轻量（转化率优先）、M 端移动协同（弱网可用）、B 端集中调度（治理优先） |
| 高并发可用 | 面向直播带货流量洪峰，可削峰、防超卖、可横向扩容 |
| 大模型防幻觉 | RAG 双路召回 + 检索片段约束，答案可溯源 |
| 多租户安全隔离 | 底层 Tenant ID 贯穿数据与权限，一村一租户、一户一身份 |
| 工程化可演示 | Docker Compose 一键拉起，便于答辩演示与后续部署 |

**核心原则：**

- **不盲目开发独立 App**：C 端用 H5 承接微信/社群私域流量，渠道订单由后端统一聚合；
- **AI 与业务解耦**：AI 能力独立成 FastAPI 服务，与高并发业务后端各自伸缩；
- **领域边界清晰**：业务（交易/库存/租户）与知识（RAG/内容）走不同数据通道。

## 3. 三端架构职责

### 3.1 C 端消费引流层（H5）

- **形态**：极致轻量、移动端优先的 H5，可嵌入微信公众号/社群分享卡片；
- **场景**：快速下单、秒杀/抢购、订单跟踪；
- **约束**：首屏体积小、弱网可用；登录尽量复用微信授权（openid）；
- **仓库目录**：`h5/`。

### 3.2 M 端移动协同层（Flutter）

- **形态**：农户/合作社安装的移动工作台（Android/iOS）；
- **场景**：
  - 语音唤醒 AI 农技问答（语音 → 转写 → RAG → 语音/图文答复）；
  - 扫码发货、入库/出库、物流交接；
  - 弱网离线缓存、断点续传；
- **约束**：本地缓存策略 + 后端幂等接口配合；
- **仓库目录**：`mobile/`。

### 3.3 B 端中枢大脑（Next.js）

- **形态**：村委/运营使用的 PC 端数据大屏与管理系统；
- **场景**：
  - RAG 知识库维护（政策 PDF 上传、切片管理、检索测试）；
  - 多租户账号分配与权限管理；
  - 多智能体策略审批（带货文案/定价建议的人工放行）；
  - 订单/库存/物流数据可视化大屏；
- **仓库目录**：`web/`。

## 4. 后端核心设计（backend · Spring Boot）

### 4.1 模块划分（建议分包）

```text
backend/
└── src/main/java/com/yuzhuang/
    ├── common/          # 通用工具、统一响应、异常处理、分布式锁
    ├── security/        # JWT 认证、租户上下文、RBAC 权限
    ├── tenant/          # Tenant ID 解析与多租户数据隔离
    ├── user/            # 用户/农户/合作社/村委
    ├── product/         # 商品、SKU、价格、促销
    ├── order/           # 订单、渠道订单聚合、集采
    ├── inventory/       # 库存、CAS 乐观锁扣减
    ├── outbox/          # Outbox 发件箱模式（事件可靠投递）
    ├── channel/         # 渠道接入抽象（H5/抖音/快手/B2B）
    └── notification/    # 站内信/微信模板消息/物流回调
```

### 4.2 高并发订单与防超卖

- **Redis Streams 削峰**：下单请求先写 Stream，消费端异步落库，避免 DB 被洪峰打满；
- **CAS 乐观锁扣库存**：`UPDATE ... SET stock = stock - n WHERE id=? AND stock >= n`，影响行数为 0 即失败重试；
- **Outbox 发件箱模式**：订单状态与"待发送事件"同事务落库，由后台任务可靠投递到 Stream / 下游，保证最终一致；
- **幂等**：订单号、渠道流水号唯一约束，支持重试。

### 4.3 全渠道聚合调度

- 统一 `OrderSource` 枚举：`H5_PRIVATE / DOUYIN / KUAISHOU / B2B_PORTAL`；
- 渠道适配器模式：`ChannelAdapter` 接口 + 各渠道实现；
- 抖音/快手公域直播流通过 OpenAPI 接入，订单回流至中台统一履约。

### 4.4 多租户数据隔离

- 每行业务数据带 `tenant_id`；
- MyBatis/JPA 层自动注入租户条件（或按租户分库），防止越权串数据；
- Redis Key 前缀携带租户标识。

## 5. AI 服务核心设计（ai-service · FastAPI）

### 5.1 RAG 检索内核

```text
PDF/政策手册 ─► 解析 ─► 结构化切片 ─► Embedding 向量化 ─► pgvector
                                                        ▲
农户语音提问 ─► 转写文本 ─► 向量召回 ─┬─► 双路召回合并 ─► 构造 Prompt
                        关键词召回 ──┘        │
                                             ▼
                        大模型(DeepSeek) 仅依据检索片段生成 ─► 引用可溯源答案
```

- **切片策略**：按标题/章节语义切分，保留元数据（来源文档、页码）；
- **双路召回**：向量相似度 + 关键词（BM25/全文索引）融合重排；
- **防幻觉约束**：Prompt 中注入"仅能使用检索片段，不得自行编造"的强约束；答案附引用；
- **向量库**：pgvector，与业务库同源便于运维。

### 5.2 电商营销多智能体（Multi-Agent Matrix）

- 接入 DeepSeek API；
- Agent 角色（示例）：
  1. **热点捕捉 Agent**：抓取平台热点与当季话题；
  2. **文案生成 Agent**：基于产品标签与热点产出小红书/抖音文案、短视频脚本；
  3. **合规质检 Agent**：校验广告法违禁词、夸大宣传、资质声明；
  4. **定价建议 Agent**：基于历史销售数据与促销日历给出动态定价区间；
- 工作流：`产品标签 + 历史数据 → 各 Agent 协同 → 合规复核 → 人工(村委/运营)审批放行`。

### 5.3 AI 服务对外接口建议

| 路径 | 说明 |
|------|------|
| `POST /ai/qa` | 农技问答（语音/文本 → RAG 答复） |
| `POST /ai/ingest` | 知识库文档上传与切片向量化 |
| `GET /ai/knowledge` | 知识库/文档/切片管理 |
| `POST /ai/marketing/generate` | 多智能体生成带货文案/脚本/定价建议 |
| `POST /ai/agents/approve` | 人工审批 Agent 产出 |
| `POST /ai/asr/transcribe` | 语音转写接入 |

## 6. 基础设施与部署（deploy）

| 服务 | 镜像 | 端口(默认) | 说明 |
|------|------|-----------|------|
| postgres | `ankane/pgvector:latest` | 5432 | 业务库 + 向量库，启用 `vector` 扩展 |
| redis | `redis:7-alpine` | 6379 | 缓存/会话/分布式锁/Streams，AOF 持久化 |
| gateway | `nginx:1.27-alpine` | 80 | 统一网关，路由见 `deploy/nginx/nginx.conf` |

- 各业务服务（backend / ai-service / web / h5）后期以 Dockerfile 加入同一 `rural-network`；
- 网关采用 **resolver + 变量式 proxy_pass**，服务未接入时返回 502 而不影响网关启动，便于渐进式接入。

## 7. 关键设计决策记录（ADR 摘要）

| 决策 | 理由 |
|------|------|
| C 端用 H5 而非独立 App | 私域（微信群/社群）分享与下单路径最短、获客成本最低 |
| AI 能力独立 FastAPI 服务 | 与高并发 Java 业务解耦，独立扩容，技术栈贴合 AI 生态 |
| 订单削峰用 Redis Streams | 相比 Kafka 更轻量，与既有 Redis 底座统一，满足参赛演示规模 |
| 库存扣减用 CAS 乐观锁 | 农产品直播场景写多读多但单 SKU 热点有限，CAS 简单可靠 |
| 事件投递用 Outbox | 保证"订单已建"与"事件已发"的事务一致性，规避双写不一致 |
| 多租户用 Tenant ID 行级隔离 | 一村/一合作社一租户，量级下足够安全且成本低 |
