## 一、结论先行

一句话结论：**项目不是“全是前端假数据”，而是“核心链路已有真实后端和数据库，但线上内容、账号、图片、支付、AI 降级和部分大屏流水仍明显处于竞赛演示状态”。**

更准确地说：

1. 商品、库存、订单、登录、看板聚合、知识库文档列表/上传都有真实 API，数据可落 PostgreSQL；订单库存扣减含 CAS、幂等键和 Outbox，不能简单说是静态页面。
2. 线上商品是 3 条种子商品；现有订单只有 3 条且全部 `CANCELLED`；累计销售额为 0；知识库文档为 0。真实数据库里承载的仍是演示内容。
3. H5 下单会真实扣库存并落订单，但没有真实支付入口，订单随后超时取消并回补库存，因此消费者闭环没有成立。
4. B 端商品管理确实能新增、编辑、改价、改库存和上下架，但没有真实商品图片上传、详情、分类、规格、运费、批量管理等能力，且下架商品会从管理列表消失，无法再从 UI 上架。
5. B 端把政府大屏、村委治理、合作社商家运营、农户访问混在同一套菜单中；当前没有“政府官方账号”角色。`FARMER` 账号实测也能读取治理大盘和租户订单。
6. AI 健康接口正常不代表 AI 能力可用。线上知识库为空，实测农技问答只返回“未检索到依据”的兜底回答且无引用；代码在未配置密钥时会使用伪随机 Mock 向量和离线营销模板。
7. 当前公网仍使用 HTTP，无 HTTPS；生产环境仍会自举公开演示账号，JWT 有代码内默认密钥；AI 知识库上传/删除没有认证。这些是上线前必须先修的 P0。

因此，若目标是参赛展示，当前工程已具备较扎实的后端骨架；若目标是政府/商家真实使用，当前只能评为“可演示原型”，不能评为“生产可用平台”。

## 二、为什么有些网址只显示 JSON

这是正常的接口分层，不是页面坏了：

| 地址 | 面向对象 | 正常返回 | 当前状态 |
|---|---|---|---|
| `/` | 人工查看的网关状态页 | HTML | 200，静态状态说明 |
| `/healthz` | Nginx/监控探针 | 纯文本 `ok` | 200 |
| `/h5/` | C 端消费者 | HTML/JS 页面 | 200 |
| `/b/login`、`/b/dashboard` | B 端管理人员 | HTML/JS 页面 | 200 |
| `/api/v1/healthz` | 业务后端探针 | JSON | 200，数据库 `UP` |
| `/ai/v1/healthz` | AI 服务探针 | JSON | 200，数据库 `connected` |
| `/ai/v1/docs` | 开发者 API 文档 | Swagger HTML | 代码已启用；生产应限制访问 |

健康检查端点的消费者是 Docker、负载均衡器、监控程序和运维脚本，机器可解析的 JSON 正是正确格式。不要把它们改成普通网页。若要提升体验，应完善 `/` 为统一入口页，展示 H5、商家端、政府端和服务状态链接。

## 五、关键问题清单

### P0：上线前必须修复

#### P0-1 AI 写接口公网匿名开放

`ai-service/app/api/knowledge.py` 明确无身份校验。任何公网调用者都能提交任意 `tenant_id` 上传文档，也能按请求体指定 `tenantId` 删除文档。QA/营销接口同样缺少认证和限流，存在数据污染、跨租户访问、资源滥用与 API 费用风险。

整改：AI 服务验证统一身份；知识上传/删除只允许授权的 `COOPERATIVE/VILLAGE`；政府只读；租户从已验证身份和授权范围推导，禁止信任表单/请求头任意租户值；匿名 QA 如确需保留，使用受控公共知识域并限流。

#### P0-2 生产环境固定演示账号和默认 JWT 密钥

`AuthDataInitializer` 没有环境 Profile/开关，服务启动即插入固定账号；登录页直接展示账号密码；`application.yml` 带可预测 JWT 默认密钥，Compose 未强制覆盖。

整改：`APP_ENV=production` 时禁止种子账号/数据；缺少高熵 JWT 密钥时启动失败；实现正式账号创建/停用/重置/首次登录改密；移除公网账号密码提示；现有线上固定密码必须轮换。

#### P0-3 没有 HTTPS 和基本边界防护

当前只有 HTTP；Nginx 无 TLS、HSTS、CSP、点击劫持防护、登录/下单/AI 限流等生产配置。JWT 存在浏览器 `localStorage`，在 HTTP/XSS 场景下风险更高。

整改：域名 + TLS；生产 Nginx 安全头和分端点限流；认证改为 `HttpOnly + Secure + SameSite` Cookie 或成熟 OIDC；若采用 Cookie 写接口，补 CSRF 防护；API 文档仅管理员或内网可见。

#### P0-4 角色权限不符合政府/商家/农户边界

后端用“所有 GET 都允许任意已登录角色”的粗粒度策略。农户可读取整个租户订单和治理大盘，可能看到收货信息；前端也没有角色路由/菜单守卫。不存在政府角色，`VILLAGE` 不能等同于政府官方账号。

整改：改为端点级权限策略与数据范围策略；新增正式政府只读角色和授权租户范围；农户只能读取自己的任务/数据；商家只能管理本租户商品订单；村委按授权治理；平台管理员负责租户/账号。后端必须是最终权限源，前端守卫只用于体验。

#### P0-5 B 端路由守卫不完整且 401 跳转路径错误

`/b/dashboard` 未登录仍能加载完整页面壳，等 API 401 后才跳转；`window.location.assign('/login')` 忽略 Next.js `basePath=/b`，公网会跳到错误的 `/login`。所有角色看到相同菜单和操作按钮。

整改：在 `/b` 范围建立统一会话与角色守卫；未登录直接到 `/b/login`；登录后按角色跳转 `/b/merchant/*`、`/b/gov/*` 等；401/403 有统一页面；隐藏无权限 UI 但仍由后端强校验。

#### P0-6 匿名下单和 SKU 作用域校验不足

下单租户来自可伪造的 `X-Tenant-Id`；库存查询按 SKU 主键，不在下单服务中验证 SKU 是否属于该店铺/共享目录。公开商品详情同样按主键直接返回，没有租户/在售状态约束。

整改：用公开店铺 slug/签名上下文解析租户；结算时服务端校验每个 SKU 的租户归属、在售状态、购买限制；公开详情只返回该店铺可见且在售商品；加下单频控、风控与审计。

### P1：核心业务闭环缺失

#### P1-1 商家端不是完整商家工作台

已有商品 CRUD 的一部分，但商品模型仅 `skuCode/spuName/price/stock/status`。缺少：

- 商品主图/轮播图上传与对象存储；
- 富文本详情、分类、单位、产地、资质证书、规格/多 SKU；
- 运费模板、服务承诺、限购、库存预警；
- 草稿、审核、发布、删除/归档、批量操作；
- 商家资料、门店/店铺页面、运营账号管理；
- 订单详情、发货信息、物流单号、售后/退款。

同时，管理页调用的商品列表只返回 `ON_SALE`，所以下架后商品从列表消失，无法再次上架。

整改：至少在现有 Next.js B 端划分 `/b/merchant` 工作台；增加独立管理查询（包含草稿/下架）；建立商品媒体资产和对象存储；完整维护商品生命周期。

#### P1-2 消费者闭环没有支付、订单中心和售后

H5 能浏览和真实下单，但没有消费者身份、购物车/多商品管理、支付、订单查询、物流跟踪、取消、退款、售后、地址簿、隐私协议。订单创建为 `STOCK_CONFIRMED`，无 H5 支付动作，线上订单因此全部超时取消。

整改：先建立支付 Provider 抽象和演示/生产模式隔离；在没有真实支付商户参数前，生产必须明确禁用交易而非伪装成功。增加订单查询凭证或消费者登录、支付结果页、订单中心、物流和售后最小闭环。

#### P1-3 政府大屏与商家运营混为一体

政府账号不应具备商品改价、库存修改、知识删除等商家操作。当前大屏数据只按单租户聚合，也没有政府跨村授权、统计口径、数据更新时间、导出、审计或脱敏。

整改：新增 `/b/gov` 只读治理大屏，只允许 `GOVERNMENT`/经授权 `VILLAGE` 进入；提供授权区域聚合、下钻、脱敏、导出审计和口径说明。商家端单独位于 `/b/merchant`。

#### P1-4 AI 线上不可验收

数据库连通的健康检查并不反映 LLM、Embedding 和知识库就绪。当前知识库为空，问答无引用；生产仍允许自动进入 Mock。

整改：区分 liveness/readiness；管理员可查看但公众不可获取敏感配置的能力状态；生产缺少真实 Embedding/LLM 配置或知识库为空时 readiness 不通过/功能明确禁用；显式 `DEMO_MODE=true` 才允许 Mock；灌入经过来源审核的真实政策/农技文档并建立评测集。

#### P1-5 大屏“实时流水”仍是假实时

经营指标是真实聚合，但 Redis Streams 流水由浏览器定时模拟，容易造成误导。

整改：接入经过鉴权的 SSE/WebSocket/短轮询真实事件；若不做，就在生产隐藏该卡片，不能继续标注实时。

#### P1-6 AI 营销审批不落库

生成结果、审批状态、审批人、版本、发布记录均未持久化。

整改：增加营销任务/输出/审批/发布审计表和 API；只有授权角色可审批；生成内容必须保持“待人工审核”直到真实审批成功。

### P2：完整性、维护性和可信度问题

- `mobile/` 仍只有 README；若产品承诺三端，必须实现最小 Flutter 工作台，否则从宣传和架构图移除。
- 抖音、快手和 B2B 只有枚举/规划，不应在成品介绍里写成“已接入”。
- README、roadmap、architecture、web README 与代码状态互相矛盾；例如 roadmap 同时说商品管理缺失/已完成、看板仍 demo/已切真实。
- 商品状态注释仍有 `ACTIVE/INACTIVE`，实现使用 `ON_SALE/OFF_SHELF`。
- 商品“产地认证”“富硒认证”等标签按名称硬编码，没有证书或审核事实，应删除或建立资质数据。
- Web/H5 各只有 2 个格式化单测；B 端 E2E 只有一个文件，权限和关键闭环覆盖不足。
- AI 3 个 QA/数据库测试依赖本地 PostgreSQL，当前环境运行时长时间不结束；应改为可重复的测试容器/明确超时。
- 没有真实压测脚本和服务级指标，无法支撑“高并发”宣传中的量化结论。
- 生产 Compose 应只暴露网关 80/443，数据库/Redis 不应映射公网接口；补备份、恢复演练和迁移回滚说明。

## 六、推荐目标架构

不建议为每个角色复制一套项目。保留现有 Spring Boot、FastAPI、Next.js、H5、PostgreSQL、Redis，通过同一 B 端代码库做清晰的角色分区：

```text
公众入口 /
├─ /h5/                  消费者商城（公开商品、购物车、支付、订单）
└─ /b/login              统一后台登录
   ├─ /b/merchant/*      合作社/商家：商品、图片、订单、物流、营销
   ├─ /b/village/*       村委：本村治理、知识审核、账号协同
   ├─ /b/gov/*           政府：授权区域只读聚合、审计、导出
   └─ /b/platform/*      平台管理员：租户、账号、角色、系统配置

Nginx/TLS
├─ Spring Boot：身份、租户、商品、订单、媒体元数据、治理聚合
├─ FastAPI：RAG、营销任务（验证同一身份和数据范围）
├─ PostgreSQL/pgvector：业务数据、授权范围、知识、审计
├─ Redis Streams：真实事件流/限流/异步任务
└─ S3 兼容对象存储：商品图片、资质、知识原文件
```

建议角色：

| 角色 | 数据范围 | 主要权限 |
|---|---|---|
| `PLATFORM_ADMIN` | 全平台，强审计 | 租户/账号/角色/配置，不参与日常商品操作 |
| `GOVERNMENT` | 明确授权的区域/租户集合 | 只读聚合、下钻（脱敏）、导出 |
| `VILLAGE` | 本村租户 | 治理看板、知识审核、协同账号 |
| `COOPERATIVE` | 本商家/合作社租户 | 商品、媒体、库存、订单、物流、营销 |
| `FARMER` | 仅本人/被分配任务 | 移动任务、库存或履约操作，不可读全租户经营和客户数据 |
| `CONSUMER`（可选） | 本人订单 | 地址、订单、支付、售后 |

政府账号必须由平台管理员审核发放，绑定可访问的行政区域/租户范围，首次登录改密，建议支持 MFA；不能再把固定 `admin/admin123` 当作政府官方账号。
